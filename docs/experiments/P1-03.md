# P1-03 상품 검색 — 인덱스 없는 `ILIKE '%q%'`

> 이 로그가 갱신되어야 이슈가 완료된 것으로 친다 (§0-6).
> 재현이 안 됐으면 안 됐다고 그대로 적는다. 수치를 만들어내지 않는다 (§0-7).

## 증상 / 가설

`GET /products?q=`가 `name.ilike('%q%') OR description.ilike('%q%')`로 20만 상품을
필터한다. Phase 0 스키마는 PK 외 인덱스가 없고(§1), 선행 와일드카드(`%q%`)라 btree가
있었어도 못 탔을 것이므로 seq scan이 될 것으로 예상. 다만 목록 엔드포인트는 같은
요청 안에서 `search_products`(P1-03) + `count_products`(P1-05, 매 요청 COUNT) +
OFFSET 페이지네이션(P1-04)이 함께 실행되므로, 세 이슈가 서로 수치를 오염시킬 수
있다는 점을 미리 유의(§ 재현 조건).

### 재현 조건 설계 메모 — 선택도(selectivity) 함정

첫 EXPLAIN 확인에서, 흔한 명사("이어폰", 매치 9,933/200,000)로만 검색하면
`ORDER BY id LIMIT 20` 때문에 planner가 PK 인덱스를 id 순으로 훑다 20건 채우고
멈춰(1.18ms) **무인덱스 문제가 역설적으로 안 보였다.** 반면 매치가 희소/0건인
검색어(오타·과세부 모델번호 등, 실사용에서 드물지 않음)는 20만 행을 사실상 전부
걸러야 끝나 300ms대로 치솟았다. `count_products`(P1-05)는 LIMIT이 없어 매치 여부와
무관하게 항상 전체를 세므로, 흔한 검색어라도 카테고리만 필터(~15ms)할 때보다
ILIKE가 있으면(~145ms) 매번 ~10배 비싸졌다. → 흔한 검색어만 쓰면 재현이 약해지므로,
희소·0건 검색어를 섞어 시나리오에 반영(코드 주석에 근거 기록).

## 원인 분석

- `Product.name`/`description`에 인덱스가 없고 `ILIKE '%q%'`는 선행 와일드카드라
  btree로도 못 탄다 — 매치가 희소/0건인 검색어는 사실상 200,000행 전수 스캔이
  필요해 300ms대로 치솟는다(EXPLAIN 확인).
- 흔한 검색어는 `ORDER BY id LIMIT`이 PK 인덱스 스캔을 조기 종료시켜 단독으로는
  빨라 보이지만(1ms대), 같은 요청 안의 `count_products`(P1-05, LIMIT 없음)는 항상
  전체를 스캔해야 하므로 ILIKE가 있으면 카테고리만 필터할 때보다 ~10배 비싸진다 —
  **P1-03(무인덱스 ILIKE)이 P1-05(매 요청 COUNT)를 통해 증폭**되는 구조.
- DB가 §13 프로파일(2 vCPU)에 묶여 있어, 50 VU 동시 요청이 CPU를 두고 경합 —
  무경합 145~308ms짜리 쿼리가 동시성 하에서 초 단위로 늘어난다.

## 트레이드오프 & 남은 한계

- **P1-03 자체(무인덱스 ILIKE)는 EXPLAIN·격리된 쿼리 지표(검색 쿼리 4,640ms→7.8ms,
  ≈594×)로 명확히 해결을 확인했다.** 그러나 k6 엔드포인트 전체 p95(17.91s)는
  백로그 기준(`p95<200ms`)에 크게 못 미친다 — **이건 P1-03의 잔여 결함이 아니라
  같은 `GET /products` 엔드포인트에 공존하는 P1-05(매 요청 COUNT, 아직 미수정)가
  이제 지배적 병목으로 드러난 것**이다. `pg_stat_statements` 상 COUNT 쿼리
  (mean 958~3,515ms)가 검색 쿼리(mean 7.8~971ms)보다 절대적으로 더 큰 비중을
  차지한다. → 결과를 그대로 기록하고 조작하지 않음(§0-7). P1-05 완료 후 이
  엔드포인트를 재검증해야 진짜 관문(p95<200ms) 통과를 확인할 수 있다.
- **`search_hit_duration`(흔한 검색어)가 Before(1.79s)보다 After 부하 중
  평균(4.99s)이 오히려 높아 보이는 것도 같은 이유** — 희소어 경로가 극적으로
  빨라지면서(3.4s→1.15s) 상대적으로 DB CPU 여유가 흔한 검색어·COUNT 경합에
  더 쓰이게 된 것으로 보인다(정확한 인과는 미검증, 추정으로 표시). 격리된
  단일 쿼리 EXPLAIN에서는 흔한 검색어 경로도 그대로 빠르다(1.36ms) — 부하 중
  수치는 "이 쿼리 자체가 느려졌다"가 아니라 "DB 전체가 여전히 포화 상태"를
  반영한다.
- **`category_id` 인덱스가 `id` 순서를 포함하지 않는 단일 컬럼 btree**라, planner가
  여전히 category+q 조합에서 `products_pkey`(id 순서) 스캔을 택하는 경우가 있다
  (EXPLAIN에서 확인). 이번 fix는 seq scan 제거가 목표라 planner의 최종 선택까지
  강제하지 않음 — 필요하면 `(category_id, id)` 복합 인덱스를 별도로 검토할 수 있으나
  범위 밖으로 남김.
- k6 시나리오가 `constant-vus`(think time 없음)로 50 VU를 끊임없이 반복 요청시켜
  "50명의 평범한 사용자"보다 훨씬 공격적인 폐루프(closed-loop) 부하다 — 백로그
  원문 그대로의 조건("50vu")을 지키기 위해 유지했지만, 실제 서비스 트래픽보다
  DB 경합을 과장할 수 있다는 점을 감안해서 위 p95 수치를 읽어야 한다.
- 3건 실패(0.12%)는 `http_req_failed` 사유 미분류 — 후속 이슈(P1-05 등) 진행 시
  같은 패턴이 반복되면 원인을 별도로 추적한다.

## 배운 것

무인덱스 `ILIKE`는 "검색어가 흔하면" 안 보일 수 있다(LIMIT+정렬 트릭으로 우연히
빨라짐) — 희소·0건 검색어를 섞어야 실제 결함이 드러난다. 그리고 같은 엔드포인트에
여러 이슈(P1-03/04/05)가 겹쳐 있을 때, 하나를 고치면 "전체 p95"가 아니라 "그
쿼리의 격리된 지표"로 성공을 검증해야 한다 — 안 그러면 옆 이슈의 잔존 병목을 이
이슈의 실패로 오판하게 된다.
