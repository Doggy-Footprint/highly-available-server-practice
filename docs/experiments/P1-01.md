# P1-01 로그인 세션 — 프로세스 내 dict 저장

> 이 로그가 갱신되어야 이슈가 완료된 것으로 친다 (§0-6).
> 재현이 안 됐으면 안 됐다고 그대로 적는다. 수치를 만들어내지 않는다 (§0-7).

## 증상 / 가설

로그인 토큰을 앱 프로세스 메모리(dict)에 저장한다. app 인스턴스를 2대 이상으로 늘리면,
로그인을 처리한 인스턴스가 아닌 다른 인스턴스로 라우팅된 `GET /auth/me` 는 그 프로세스의
dict 에 토큰이 없어 401 을 낸다. 요청이 여러 인스턴스로 흩뿌려질수록(N 대 중 로그인
인스턴스가 아닌 곳으로 갈 확률 = (N-1)/N) 401 비율이 올라갈 것으로 예상.

## 심은 지점 & 검증 승인

|---|---|

| INTENDED-ISSUE 위치 | `app/auth/service.py:19` — `grep -rn "INTENDED-ISSUE: P1-01"` → 1건, 정확히 dict 선언부 위 |

| 승인 일시 | 2026-07-18 11:2x KST (사용자 승인 — "승인, measure 진행") |

### 재현 조건 조정 — 1차 실패, 원인은 k6 커넥션 재사용

1차 실행(`noConnectionReuse` 없이) 결과: `me_401_rate = 0.00%` (4072건 전부 200).
verify-break 를 통과했으므로("문제가 제대로 안 심겼다"보다) 재현 조건 쪽을 먼저 의심함.

원인: k6 는 기본적으로 **VU 당 TCP 커넥션을 keep-alive 로 재사용**한다. nginx 의 동적
`proxy_pass`(`resolver 127.0.0.11 valid=5s`, §11)는 **새 커넥션을 열 때만** 백엔드 주소를
다시 고른다. 즉 한 VU 가 로그인 요청에서 연 커넥션을 이후 `/auth/me` 호출까지 그대로
재사용하면, 그 VU 의 모든 요청이 로그인 때 잡힌 백엔드 한 곳에 고정되어 버려 문제가
가려진다. `options.noConnectionReuse = true` 로 매 요청마다 새 커넥션(`Connection: close`)을
열도록 강제한 뒤 재실행 — 아래 Before 수치.

## 원인 분석

- `_SESSIONS` 가 프로세스 전역 변수라, app 컨테이너 3대는 서로 다른 dict 를 갖는다.
- app ×3, 요청이 균등 분산된다고 가정하면 로그인 인스턴스가 아닌 곳으로 갈 확률은
  이론상 (3-1)/3 ≈ 66.7% — 실측 68.04% 로 근접. nginx 동적 DNS 라운드로빈이 대체로
  균등하게 흩뿌리고 있다는 뜻으로 해석(확인된 사실). 정확히 66.7%가 아닌 차이는
  DNS 응답 순서·k6 VU 스케줄링의 표본 편차로 추정(추측, 별도 확인 안 함).
- `me_instance_mismatch = 0` 은 가설을 뒷받침하는 사실 확인: 200 이 나온 요청은 예외
  없이 로그인 인스턴스와 동일한 곳에서 처리됐다 — dict 가 정말로 프로세스에 갇혀
  있다는 직접 증거.
- p99 652ms~4.71s 롱테일은 `/auth/me` 자체가 아니라 이 시나리오가 매 이터레이션마다
  `signup`(bcrypt 12 hash)까지는 아니고 최초 1회만 돌지만, **login 은 매 요청 전 1회씩만
  발생**(토큰 캐시 이후 재로그인 없음)하므로 이 꼬리는 signup/login 경로의 bcrypt 비용
  (P1-10, `app/auth/service.py:44` 별도 표식) 이 30VU 동시 시작 구간에 몰려 나타난
  것으로 추정 — P1-01 자체와는 무관한 인접 이슈 잡음(추측, P1-10 measure 시 별도 확인).

## 수정

- 커밋: `1809b21` `fix(P1-01): 로그인 세션을 Redis로 이전 — stateless화 (401률 68.04%→0% @app x3)`
- 무엇을 바꿨는가:
  - `app/auth/service.py`: 프로세스 전역 `_SESSIONS: dict[str, int]` 제거. `login()` 은
    `redis.set(f"session:{token}", user.id, ex=86400)` 로 토큰을 Redis 에 저장(TTL 24h).
    `get_current_user()` 는 `redis.get(f"session:{token}")` 으로 조회 — 어느 인스턴스가
    처리하든 동일한 Redis 를 보므로 결과가 같다.
  - `app/auth/router.py`: `/auth/login` 엔드포인트에 `Redis = Depends(get_redis)` 주입,
    `service.login(session, redis, ...)` 로 전달.
  - `app/core/redis.py` 의 기존 `get_redis()` 싱글턴(이미 Phase 0 스캐폴딩에 준비돼 있던 것,
    `socket_timeout=1.0`) 을 그대로 재사용 — 새 인프라 추가 없음.
  - `INTENDED-ISSUE: P1-01` 주석 제거. 바로 아래 있던 `INTENDED-ISSUE: P1-10`(bcrypt CPU
    블로킹, 별개 이슈)은 손대지 않음 — `grep -rn "INTENDED-ISSUE"` 총 22→21건으로 정확히
    1건만 줄어든 것으로 확인.

## 트레이드오프 & 남은 한계

- **Redis 가 새로운 단일 장애점이 됐다.** 세션이 Redis 에 있으므로 Redis 가 죽으면 로그인
  사용자 전원이 인증 불가(P2-13 의 소재). Phase 0→1 전환에서 감수하는 트레이드오프이고,
  graceful degradation 은 P2-13 에서 다룬다.
  - 실측으로도 확인됨: fix 검증 1차 실행(컨테이너 막 재기동한 직후)에서 `/auth/login` 3건이
    `redis.exceptions.TimeoutError: Timeout reading from redis:6379` 로 500 을 냄
    (`get_redis()` 의 `socket_timeout=1.0`). 스택이 완전히 웜업된 뒤 재실행하면 0건 —
    콜드스타트 노이즈로 판단해 재현 조건에서 제외했지만, "Redis 응답 지연 시 로그인
    500" 자체는 이번 fix 가 만든 실제 동작이고 P2-13/P2-14 에서 다시 마주칠 지점이다.
- 세션 TTL 24h 는 임의값 — 로그아웃/토큰 무효화 API 는 아직 없다(백로그에도 없음, 범위 밖).
- JWT 대신 Redis 세션을 택했다 — 검증 시 Redis 왕복이 매 요청 붙는다(`get_current_user`
  가 요청마다 GET 1회). JWT 였다면 이 왕복은 없앨 수 있었지만 즉시 폐기(로그아웃)가
  어려워진다. 아키텍처 로드맵(§1)이 이미 "Redis(session, cache)"로 못 박아 둔 방향이라
  이걸 따름 — 트레이드오프 판단 자체는 이미 상위에서 내려진 상태.

## 배운 것

k6 는 VU 당 커넥션을 기본적으로 keep-alive 재사용하므로, nginx 의 동적 DNS 기반
로드밸런싱처럼 "커넥션 단위로 백엔드가 고정되는" 구성을 재현할 때는
`noConnectionReuse: true` 없이는 인스턴스 분산 자체가 가려질 수 있다.
