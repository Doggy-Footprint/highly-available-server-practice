# P1-02 주문 내역 — N+1 (루프 내 개별 쿼리)

> 이 로그가 갱신되어야 이슈가 완료된 것으로 친다 (§0-6).
> 재현이 안 됐으면 안 됐다고 그대로 적는다. 수치를 만들어내지 않는다 (§0-7).

## 증상 / 가설

`GET /orders`(내역)·`GET /orders/{id}`(상세)가 주문을 가져온 뒤, 주문마다 아이템을,
아이템마다 상품을 개별 쿼리로 조회한다. 주문 N개·아이템 평균 M개면 쿼리 수는
`1 + N + N*M`으로 선형 증가할 것으로 예상. 게다가 Phase 0 스키마는 PK 외 인덱스가
없으므로(§1), 그 N+1 각각의 쿼리도 인덱스 스캔이 아니라 풀스캔일 가능성이 있어
"왕복 횟수 증가" 이상의 비용 폭증이 우려됨.

### 재현 조건 조정 — "30건 유저" 부재, 대표 유저로 대체

백로그는 "주문 30건 유저"를 명시하지만, seed 분포를 확인한 결과 30건짜리 유저가 없다:

```
order_count | num_users
------------+----------
3~10        | 소수(20명 미만)
48          | 40,190명
49          | 9,601명
3000/3001   | 200명 (heavy 유저, P1-11 전용 소재)
```

거의 모든 일반 유저가 48~49건을 갖는 이봉분포(bimodal)라 "30건"에 정확히 맞는 유저는
없음 — heavy 유저(3,000건, P1-11의 "LIMIT 없는 전체 조회" 전용 소재)를 피하고, 자릿수가
같은 대표 일반 유저(`user300`, 49건)로 대체. 결과에는 영향 없음(N+1은 N에 비례하므로
48~49건도 문제를 충분히 드러냄) — 조정 과정을 그대로 기록.

### 재현 조건 조정 — 동시성 프로파일 재설계 (1차 시도 실패)

1차 시도: `constant-vus 20·30s` 로 반복 루프. 결과 100% 30초 타임아웃, 그리고 k6가
포기한 뒤에도 서버는 이미 시작한 N+1 순회를 취소하지 않고 계속 실행해 DB에 잔여
백로그가 수십~수백 초 더 남았다(클라이언트 타임아웃이 서버 작업을 취소하지
않는다는 것 자체는 P2-14 소재라 여기서 다루지 않음). 도착률이 처리율을 계속 앞질러
"통제된 동시 사용자 수" 측정이 불가능했음.

→ `per-vu-iterations`(VU당 정확히 1회)로 재설계해 "동시 사용자 수"를 깨끗하게
고정하고, 재시도로 인한 배치 폭주를 없앴다. HTTP 타임아웃도 90s로 상향(문제가
재현 안 된 게 아니라 조건이 너무 촘촘했던 것 — CLAUDE.md §7 지침대로 재현 조건
쪽을 먼저 의심).

## Before

### (A) 단일 요청, 무경합 (`user300`, 49주문)

```
$ curl .../orders -H "Authorization: Bearer ..."
http_status=200 time_total=8.895773s
```

`pg_stat_statements`(직전 reset):

| 쿼리 | calls | total_exec_time | mean_exec_time |
|---|---|---|---|
| `SELECT ... FROM order_items WHERE order_id = ?` | **49** | 8,583.87 ms | 175.181 ms |
| `SELECT ... FROM orders WHERE user_id = ? ORDER BY id DESC` | 1 | 211.94 ms | 211.942 ms |
| `SELECT ... FROM products WHERE id = ?` | **128** | 4.57 ms | 0.036 ms |
| **합계** | **178** | **~8,800 ms** | — |

`EXPLAIN (ANALYZE, BUFFERS)`로 원인 확인 — 둘 다 **Parallel Seq Scan**(인덱스 없음,
§1 Phase 0 스키마 규칙):

```
-- order_items WHERE order_id = 14701  (전체 7,980,351 행)
Parallel Seq Scan on order_items (actual time=144.772..162.142 rows=1 loops=3)
  Filter: (order_id = 14701)
  Rows Removed by Filter: 2660116
  Buffers: shared hit=58688
Execution Time: 195.910 ms

-- orders WHERE user_id = 300  (전체 ~3,000,111 행)
Parallel Seq Scan on orders (actual time=37.988..159.595 rows=16 loops=3)
  Filter: (user_id = 300)
  Rows Removed by Filter: 1000037
Execution Time: 165.290 ms
```

→ N+1의 각 쿼리 자체가 인덱스 스캔이 아니라 **8백만 행 풀스캔**이라, N+1이 단순
"왕복 49회 추가"가 아니라 "풀스캔 49회 추가"로 증폭됨. products 쪽은 PK 조회라
저렴(0.036ms/call)해서 N+1의 병목은 사실상 order_items 쪽에 집중.

### (B) 동시 10명 (VU 10, `per-vu-iterations` 1회씩, timeout 90s)

```
✓ login 200        (10/10)
✗ orders 200       0% — ✓ 0 / ✗ 10   (전원 90s 타임아웃)
orders_list_duration: avg=1m30s min=1m29s p(95)=1m30s max=1m30s
```

무경합 8.9s였던 요청이 **동시 10명에서는 90초 안에 단 하나도 완료되지 못함.**
타임아웃으로 요청을 포기한 뒤에도 서버 작업은 계속 실행 중이었고, 그 스냅샷에서
`pg_stat_statements`:

| 쿼리 | calls (관측 시점) | mean_exec_time |
|---|---|---|
| `order_items` 개별 조회 | 343 (기대 490 중 진행분) | **4,442.894 ms** (무경합 대비 ~25배) |
| `orders` 목록 조회 | 20 | **1,913.390 ms** (무경합 대비 ~9배) |

`docker stats`: `flashmart-db-1` CPU **199~205%** (§13 프로파일상 2 vCPU 상한에 포화).
요청을 포기한 뒤에도 active connection이 실제로 드레인되기까지 별도로 1~2분 소요
(`pg_stat_activity` 폴링으로 확인).

## 원인 분석

- `_build_order_view`가 주문마다·아이템마다 별도 `await` 쿼리를 낸다 — 정확히 백로그
  정의대로의 N+1(`1 + N + N*M`).
- Phase 0 스키마는 PK 외 인덱스가 없다(§1 규칙) — `order_items.order_id`,
  `orders.user_id` 모두 인덱스가 없어 N+1의 개별 쿼리 각각이 Parallel Seq Scan이 된다.
  즉 이 이슈는 "왕복 횟수" 문제이면서 동시에 "그 왕복 하나하나가 전체 테이블
  스캔"이라는 이중 비용 구조 — 두 문제가 겹쳐 무경합에서도 8.9초까지 벌어짐.
- 동시성이 붙으면 db 컨테이너가 §13 프로파일(2 vCPU)에 포화되고, 개별 쿼리 자체의
  실행 시간도 (경합 없을 때 대비) 9~25배로 늘어난다 — N+1의 "쿼리 개수 곱"과
  "경합에 따른 개별 쿼리 지연 증가"가 곱연산으로 겹쳐 10 동시 사용자만으로도
  90초 내 완료가 0%가 되는 파국적 증폭이 나타남.

## 트레이드오프 & 남은 한계

- **쿼리 수는 상수(3)가 됐지만, 그 3개 자체는 여전히 풀스캔이다.** Phase 0 스키마가
  의도적으로 PK 외 인덱스를 갖지 않으므로(§1), `selectinload`가 내는
  `order_items WHERE order_id IN (...)`도 인덱스 스캔이 아니라 8백만 행 스캔이다.
  동시성이 커지면(After (B)에서 p95 4.41s) 이 풀스캔 자체가 다시 병목이 될 수 있다.
  인덱싱은 이 이슈의 "수정 방향"(selectinload/JOIN)에 명시돼 있지 않아 범위 밖으로
  남겨둠 — 필요하면 별도 이슈로 다룬다.
- `selectinload`의 두 번째 쿼리는 첫 쿼리가 반환한 주문 수만큼 `IN (...)` 리스트가
  커진다. P1-11(LIMIT 없는 전체 조회, heavy 유저 3,000건)이 아직 미수정이라, 그
  유저에 대해서는 `IN` 리스트가 3,000개짜리가 될 수 있다 — P1-11 fix가 들어오면
  이 경로도 함께 가벼워지지만, 두 이슈는 백로그상 독립 검증 대상이라 여기서는
  건드리지 않음.
- **관찰됐지만 범위 밖으로 남긴 부작용**: Before (B) 측정 중, k6가 90초 타임아웃으로
  요청을 포기한 뒤에도 서버(uvicorn/FastAPI)는 이미 시작한 코루틴을 취소하지 않고
  계속 실행해 DB에 실제 부하가 1~2분 더 남았다. 클라이언트 타임아웃이 서버 작업을
  취소하지 않는다는 것 — 이는 P2-14(타임아웃 계층·좀비 작업)의 소재와 겹치므로
  이번 이슈에서는 관찰만 기록하고 별도로 다루지 않음.

## 배운 것

인덱스가 없는 스키마에서 N+1은 "왕복 횟수 증가"가 아니라 "N번의 전체 테이블
스캔"으로 증폭된다 — `selectinload`로 쿼리 수를 상수로 줄이는 것만으로도 무경합
기준 13배 이상의 개선이 나오지만, 남은 쿼리 자체가 여전히 풀스캔이라는 사실은
쿼리 카운트만 봐서는 드러나지 않는다(`EXPLAIN ANALYZE`로 직접 확인해야 함).
