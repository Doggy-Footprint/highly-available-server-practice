## 1. 현상 및 요구사항 진단 (Problem & Context)

- **관측된 병목 지표 (`Before`)**:
  - `EXPLAIN (ANALYZE, BUFFERS)`:
    - `OFFSET 0` (`page=0`): `rows=20`, `Buffers: shared hit=5`, `0.126 ms`
    - `OFFSET 100000` (`page=5000`): `rows=100020`, `Buffers: shared hit=3856`, `26.557 ms`
    - `OFFSET 190000` (`page=9500`): `rows=190020`, `Buffers: shared hit=7397`, `34.028 ms`
  - `k6` (`load/k6/p1-04.js`, `target` 30 VU · 1m):
    - 전체 `p95 = 890.16ms` (`shallow p95 = 590.78ms` vs `deep p95 = 898.00ms`)
    - `pg_stat_statements`: 목록 조회 쿼리 평균 `185.15ms` (호출당 평균 `4,414` 블록 스캔)
- **근본 원인 (Root Cause)**:
  - `OFFSET(page * size)` 페이지네이션은 인덱스가 있어도 앞선 `page * size`개의 행을 실제로 스캔하고 버려야 하므로 탐색 깊이에 비례해 버퍼 읽기와 응답 지연이 선형으로 증가한다.

---

## 2. 아키텍처 설계 및 선택 근거 (Architecture & Rationale)

- **선택한 후보 및 이유 (3~5줄)**:
  - **후보 B (Cursor 전면 전환)** 채택.
  - 훈련 목적에 맞게 레거시 `OFFSET`(`page`) 분기를 남기지 않고 단일 Keyset(Cursor) 경로로 깔끔하게 전환한다.
- **마지막 페이지(`next_cursor=None`) 판별 방식**:
  - 동시 삽입/삭제 상황이나 딱 떨어지는 페이지 경계에서도 안전하도록, 실제 다음 행 존재 여부를 확인하여 더 이상 다음 행이 없을 때 확실하게 `next_cursor=None`을 반환한다.
- **계층별 확정 명세 (Candidate B — Cursor 전면 전환)**:
  - **[1/4] [`app/products/schemas.py`](../../app/products/schemas.py) (`ProductListResponse`)**:
    - 기존 `page: int` 필드를 제거하고 `next_cursor: int | None` 필드로 교체 (`total`, `size`, `next_cursor`, `items`).
  - **[2/4] [`app/products/router.py`](../../app/products/router.py) (`list_products`)**:
    - 기존 `page` 쿼리 파라미터를 제거하고 `cursor: int | None = Query(default=None, ge=1)`(양수 상품 ID만 허용)을 받아 `service.list_products`로 전달.
  - **[3/4] [`app/products/service.py`](../../app/products/service.py) (`list_products`)**:
    - 다음 페이지 존재 여부를 판별해 실제로 다음 행이 있을 때만 현재 페이지 마지막 아이템의 `id`를 `next_cursor`로 설정하고, 없으면 `None`으로 설정.
  - **[4/4] [`app/products/repository.py`](../../app/products/repository.py) (`search_products`)**:
    - `offset(page * size)`를 제거하고, `cursor`가 주어졌을 때 `Product.id > cursor` 조건과 `Product.id` 오름차순 정렬로 조회.
