# P1-01 — 로그인 세션이 프로세스 메모리에 갇히는 문제 (해결됨)

- **범위**: 로그인/인증 (`POST /auth/login`, `GET /auth/me`)
- **커밋**: break `28f23c2` → measure `bd2b003` → fix `1809b21`
- **상태**: 해결 — `GET /auth/me` 401률 **68.04% → 0.00%** (app ×3, 30VU·40s)
- **상세 로그**: `docs/experiments/P1-01.md`

---

## 1. 문제 설명

로그인에 성공하면 서버는 토큰을 발급하고, 그 토큰이 어떤 사용자인지를 어딘가에
저장해뒀다가 이후 요청(`GET /auth/me` 등 인증이 필요한 모든 엔드포인트)에서 다시
찾아봐야 한다. Phase 0 구현은 이 저장소를 **앱 프로세스 메모리의 dict**로 뒀다:

```python
# app/auth/service.py (수정 전)
_SESSIONS: dict[str, int] = {}          # 토큰 → user_id, 프로세스 전역

async def login(...):
    token = secrets.token_urlsafe(32)
    _SESSIONS[token] = user.id          # 이 프로세스의 메모리에만 저장
    return token

async def get_current_user(...):
    user_id = _SESSIONS.get(token)      # 이 프로세스의 메모리에서만 조회
```

app 인스턴스가 1대뿐이면 문제가 없다. 하지만 이 서비스는 §5 로드맵상 Phase 1부터
`nginx + app ×3` 구성으로 수평 확장한다. 인스턴스가 여러 개면 각자 독립된 dict를
가지므로, **로그인을 처리한 인스턴스와 다른 인스턴스로 라우팅된 요청은 토큰을 못
찾아 401을 낸다.** 사용자 입장에서는 "방금 로그인했는데 새로고침하면 랜덤하게
로그아웃되는" 것처럼 보인다. 이건 흔한 안티패턴이다 — 로컬 개발(인스턴스 1대)에서는
절대 드러나지 않고, 스케일아웃하는 순간 터진다.

## 2. 재현 경로

1. **구성**: `make up N=3` — app 컨테이너 3대 + nginx LB(§13 리소스 프로파일: app 각
   1.0 vCPU/512m, `docker stats`로 실제 제한 적용 확인).
2. **시나리오** (`load/k6/p1-01.js`): VU마다 신규 유저를 signup→login 하고, 응답에 실린
   `instance_id`(호스트명, `app/core/config.py`)로 "어느 인스턴스가 로그인을 처리했는지"
   기록한다. 이후 같은 토큰으로 `GET /auth/me`를 반복 호출하며 두 가지를 센다:
   - `me_401_rate` — 401 비율 (문제가 있으면 0보다 커야 함)
   - `me_instance_mismatch` — 200인데 응답의 `instance_id`가 로그인 인스턴스와 다른 경우
     (수정 전엔 0이어야 정상 — 다르면 애초에 dict가 프로세스에 갇혀 있지 않다는 뜻이므로)
3. **함정 — 1차 시도는 재현 실패(401 0%)**: k6는 VU당 TCP 커넥션을 기본적으로
   keep-alive로 재사용한다. nginx의 동적 `proxy_pass`(Docker DNS `resolver`)는 **새
   커넥션을 열 때만** 백엔드를 다시 고르므로, 커넥션이 재사용되면 한 VU의 모든 요청이
   로그인 때 잡힌 백엔드 하나에 고정돼 문제가 가려진다. k6 옵션
   `noConnectionReuse: true`로 매 요청 새 커넥션을 강제한 뒤에야 재현됐다.
   (verify-break를 이미 통과한 상태였으므로 "문제가 안 심겼다"가 아니라 "재현 조건이
   약하다" 쪽을 먼저 의심한 것 — CLAUDE.md §7의 지침대로.)

## 3. 측정 방법 (Before)

`make load S=p1-01` (30VU·40s, app ×3) 실행 후 k6 요약과 커스텀 메트릭을 확인.

| 지표 | 값 |
|---|---|
| `me_401_rate` | **68.04%** (2890/4247) — 이론치 (N-1)/N = 3대 중 2/3 ≈ 66.7%에 근접 |
| `me_instance_mismatch` (200인데 인스턴스 다름) | **0** — 성공한 요청은 전부 로그인 인스턴스와 동일. dict가 프로세스에 갇혀 있다는 직접 증거 |
| `http_req_failed` | 67.10% |

## 4. 수정 방법

수정 방향은 프로젝트 아키텍처 로드맵(§1)에 이미 "Phase 1: Redis(session, cache)"로
정해져 있었고, `app/core/redis.py`에 `get_redis()` 싱글턴(타임아웃 명시)도 Phase 0
스캐폴딩 단계에서 미리 준비돼 있었다 — 그걸 실제로 연결하기만 하면 됐다.

- **`app/auth/service.py`**: `_SESSIONS` dict 제거. 토큰을 Redis 키(`session:<token>`,
  TTL 24h)로 저장/조회하도록 변경. `login()`은 `redis.set(...)`, `get_current_user()`는
  `redis.get(...)`.
- **`app/auth/router.py`**: `/auth/login`에 `Redis = Depends(get_redis)` 주입, 서비스
  함수로 전달.
- 인접해 있던 `INTENDED-ISSUE: P1-10`(로그인 bcrypt가 이벤트 루프를 CPU로 블로킹하는
  문제) 표식은 **건드리지 않음** — 별개 이슈, 이번 수정 범위 밖 (한 번에 이슈 하나만
  다룬다는 §0-5 원칙).

## 5. 결과 (After)

동일 시나리오(`load/k6/p1-01.js`, app ×3) 재실행:

| 지표 | Before | After |
|---|---|---|
| `me_401_rate` | 68.04% | **0.00%** (0/4056) |
| `me_instance_mismatch` | 0 | **2730** (67.7%) — 다른 인스턴스로 라우팅돼도 정상 200 → 세션이 인스턴스 경계를 넘어 실제로 공유됨을 확인 |
| `http_req_failed` | 67.10% | **0.00%** |

회귀 확인: `make load S=mixed N=3 PROFILE=smoke` — checks 100%(426/426),
`http_req_failed` 0%(0/490). 목록/상세/검색/주문/내역/로그인 전 경로 정상.

**남은 트레이드오프**: Redis가 새로운 단일 장애점이 됐다. 실제로 fix 검증 중 컨테이너
재기동 직후 로그인 3건이 `redis.exceptions.TimeoutError`(소켓 타임아웃 1s)로 500을
낸 사례를 관찰했다(웜업 후 재실행에서는 재현 안 됨, 콜드스타트로 판단해 최종 재현
조건에서는 제외). 이 자체는 이번 fix가 만들어낸 실제 동작이고, Redis 장애 주입
graceful degradation은 P2-13에서 다룬다.
