# P1-02 — 주문 내역의 N+1 쿼리 (해결됨)

- **범위**: 주문 내역/상세 (`GET /orders`, `GET /orders/{id}`)
- **상태**: 해결 — 요청당 쿼리 수 **178 → 3**, 무경합 지연 **8.90s → 0.67s** (`user300`, 49주문)
- **상세 로그**: `docs/experiments/P1-02.md`

---

## 1. 문제 설명

주문 내역을 보여주려면 주문 → (주문에 속한) 아이템 → (아이템의) 상품, 세 단계 정보가
필요하다. Phase 0 구현은 이 세 단계를 각각 별도 쿼리로, 그것도 **루프 안에서 주문마다·
아이템마다 개별 호출**했다:

```python
# app/orders/service.py (수정 전)
async def _build_order_view(session, order):
    items = await repository.get_order_items(session, order.id)   # 주문마다 1쿼리
    for it in items:
        product = await product_repo.get_product(session, it.product_id)  # 아이템마다 1쿼리
        ...

async def list_orders(session, user):
    orders = await repository.list_orders_for_user(session, user.id)  # 1쿼리
    views = [await _build_order_view(session, order) for order in orders]  # 루프
```

주문이 N개, 주문당 아이템이 평균 M개면 쿼리 수는 `1 + N + N*M`으로 선형 증가한다.
이 프로젝트의 Phase 0 스키마는 **PK 외 인덱스를 의도적으로 두지 않기** 때문에
(`CLAUDE.md` §1), N+1의 개별 쿼리 하나하나가 "저렴한 인덱스 조회"가 아니라
"800만 행짜리 테이블 전체 스캔"이었다 — 그래서 이 문제는 왕복 횟수 증가보다 훨씬
치명적으로 증폭됐다.

## 2. 재현 경로

1. **구성**: `make up N=3` — app 3대 + nginx LB, §13 리소스 프로파일(app 각 1vCPU/512m,
   db 2vCPU/4g) 그대로.
2. **시나리오** (`load/k6/p1-02.js`): seed의 일반 유저(`user300`, 주문 49건 — 백로그가
   예시로 든 "30건"에 정확히 맞는 유저가 seed에 없어, 자릿수가 같은 대표 유저로 대체.
   heavy 유저(3,000건)는 P1-11 전용 소재라 제외)로 `GET /orders`를 반복 호출.
3. **측정 두 갈래**:
   - (A) 단일 요청, 무경합 — 순수 N+1 비용만 관찰.
   - (B) 동시 10명(VU 10, `per-vu-iterations` 1회씩) — 동시성 하 증폭 관찰.
4. **함정 — 1차 시도(constant-vus 20·30s)는 신호가 아니라 잡음**: 무경합에서도
   요청 하나가 초 단위로 걸리는 상황에서 반복 루프 executor를 쓰면 도착률이 처리율을
   곧장 앞질러 전원 타임아웃, 게다가 k6가 포기해도 서버는 이미 시작한 작업을 계속
   실행해 DB에 잔여 백로그가 수십~수백 초 남았다. `per-vu-iterations`(VU당 정확히
   1회)로 바꿔 "동시 사용자 수"를 통제된 스냅샷으로 측정했다.

## 3. 측정 방법 (Before)

`pg_stat_statements_reset()` → 요청 실행 → 집계 쿼리로 호출 수·실행시간 확인,
`EXPLAIN (ANALYZE, BUFFERS)`로 개별 쿼리의 실행계획 확인.

### (A) 단일 요청, 무경합

| 지표 | 값 |
|---|---|
| 응답 시간 (`curl time_total`) | **8.90 s** |
| 쿼리 수 | **178** (`orders` 1 + `order_items` 49 + `products` 128) |
| `order_items` 쿼리 원인 | `EXPLAIN`: **Parallel Seq Scan**, 800만 행 중 필터로 266만 행 제거/워커, 인덱스 없음(§1) |
| `orders` 쿼리 원인 | 마찬가지로 Parallel Seq Scan, 300만 행 |

### (B) 동시 10명 (90초 타임아웃)

| 지표 | 값 |
|---|---|
| `orders 200` 성공률 | **0%** (0/10) — 전원 90초 타임아웃 |
| DB 컨테이너 CPU | **199~205%** (§13 프로파일 2 vCPU 상한 포화) |
| `order_items` 쿼리 평균 실행시간(경합 중 스냅샷) | **4,442 ms** (무경합 대비 ~25배) |
| 타임아웃 후 DB 잔여 백로그 드레인 시간 | 1~2분 |

## 4. 수정 방법

- `app/orders/repository.py`: `list_orders_for_user()`·`get_order()`에
  `.options(selectinload(Order.items).selectinload(OrderItem.product))` 추가 —
  SQLAlchemy가 `order_id IN (...)`/`product_id IN (...)` 형태의 **배치 쿼리**를
  자동 생성하게 함. N+1의 소재였던 `get_order_items()`는 호출부가 사라져 삭제.
- `app/orders/service.py`: `_build_order_view()`가 더 이상 쿼리를 내지 않고, repository가
  이미 eager-load 해둔 `order.items`/`it.product` 관계를 그대로 읽어 뷰를 조립하는
  순수 함수로 변경(`async def` → `def`). 미사용 `product_repo` import 제거.
  `INTENDED-ISSUE: P1-02` 주석 제거.
- 인접한 `INTENDED-ISSUE: P1-11`(LIMIT 없는 전체 조회) 표식은 건드리지 않음 — 별개
  이슈, 이번 수정 범위 밖.

## 5. 결과 (After)

### (A) 단일 요청, 무경합 (조건 동일)

| 지표 | Before | After |
|---|---|---|
| 응답 시간 | 8.90 s | **0.67 s** (≈13.4×) |
| 쿼리 수 | 178 | **3** |
| DB 총 실행시간 | ~8,800 ms | ~563 ms (≈15.6×) |

응답 바이트는 Before/After 완전히 동일(diff 없음) — 데이터 정합성 유지 확인.

### (B) 동시 10명 (조건 동일)

| 지표 | Before | After |
|---|---|---|
| `orders 200` 성공률 (90s 내) | 0% (0/10) | **100%** (8/8, 로그인 성공분 전원) |
| 전체 러너 완주 시간 | ≥90 s (타임아웃) | **5.4 s** |
| `orders` p95 지연 | 측정 불가(전원 타임아웃) | 4.41 s |
| 러너 종료 후 DB 잔여 백로그 | 1~2분 | 없음 |
| 요청당 쿼리 수 (동시성 하) | — | **3 유지** (`pg_stat_statements` 8회/8회, 성공 요청 수와 정확히 일치) |

### 회귀 확인

`make load S=mixed N=3 PROFILE=smoke`: checks 100%(665/665), `http_req_failed` 0%,
p95 2.68s·p99 3.94s. 목록/상세/검색/주문/내역/로그인 전 경로 정상 — P1-01 검증
시점 baseline(p95 4.95s·p99 16s, 당시 "P1-02 등 미수정 병목" 명시)보다 개선돼
이번 fix가 mixed 트래픽 꼬리 지연에도 기여함을 뒷받침.

## 6. 요약

세 단계로 나뉜 조회(주문→아이템→상품)를 루프 안에서 각각 개별 쿼리로 요청하던
것을 SQLAlchemy `selectinload`로 배치 쿼리 2개(+원본 목록 쿼리 1개, 총 3개 고정)로
합쳤다. 이 스키마는 보조 인덱스가 없어 N+1의 개별 쿼리 하나하나가 풀스캔이었기
때문에, 단순 "왕복 횟수 감소"보다 훨씬 큰 개선(무경합 13배, 동시 10명에서
"0% 완료"→"100% 완료·5.4초")으로 나타났다. 다만 남은 3개 쿼리 자체는 여전히
풀스캔이라(인덱싱은 이 이슈의 수정 범위 밖) 동시성이 커지면 다시 병목이 될 수
있다는 한계가 있다 — 상세는 `docs/experiments/P1-02.md`의 "트레이드오프" 참고.
