# P1-03 — 상품 검색의 무인덱스 `ILIKE` (해결됨, 단 부분적)

- **범위**: 상품 검색 (`GET /products?q=`)
- **상태**: P1-03 자체(무인덱스 ILIKE)는 해결 — 격리된 검색 쿼리 지연 **4,640ms → 7.8ms**
  (≈594×, 부하 중 평균). 단, 같은 엔드포인트의 **p95는 여전히 목표(200ms) 미달** —
  잔존 원인은 이 이슈가 아니라 미수정 상태인 P1-05(매 요청 `COUNT(*)`)
- **상세 로그**: `docs/experiments/P1-03.md`

---

## 1. 문제 설명

상품 검색은 `name`/`description`을 `ILIKE '%q%'`로 필터한다. Phase 0 스키마는
PK 외 인덱스를 의도적으로 두지 않고(`CLAUDE.md` §1), 게다가 선행 와일드카드
(`%q%`)라 일반 btree 인덱스가 있었어도 타지 못한다:

```python
# app/products/repository.py (수정 전)
if q:
    pattern = f"%{q}%"
    stmt = stmt.where(Product.name.ilike(pattern) | Product.description.ilike(pattern))
```

20만 상품 테이블에서 이 조건은 최악의 경우(매치 희소·0건) 전체 행을 걸러야
"결과 없음"을 확정할 수 있어 사실상 seq scan과 동급 비용이 든다.

## 2. 재현 경로

1. **구성**: `make up N=3` — app 3대 + nginx LB, §13 리소스 프로파일 그대로.
2. **시나리오** (`load/k6/p1-03.js`): `GET /products?q=...&page=0`을 흔한 명사
   검색어(70%, 매치 ~5%)와 희소·오타 검색어(30%, 매치 희소~0건)로 섞어 요청,
   50% 확률로 `category` 동반. 50 VU(백로그 원문 조건 그대로).
3. **재현 조건 함정 — 선택도(selectivity)**: 흔한 검색어만 쓰면 `ORDER BY id
   LIMIT` 조합 때문에 planner가 PK 인덱스로 20건을 조기에 채워 문제가 안
   보인다(1ms대). 희소·0건 검색어를 섞어야 실제 결함(수백 ms대)이 드러난다.

## 3. 측정 방법 (Before)

`EXPLAIN (ANALYZE, BUFFERS)`로 단일 쿼리 실행계획 확인 + `pg_stat_statements`로
부하 중 쿼리별 호출 수·평균 실행시간 확인 + k6 `p1-03.js`(smoke 10VU, target
50VU·3m)로 엔드포인트 전체 지연 확인.

| 지표 | 값 |
|---|---|
| EXPLAIN — 희소어 검색 단일 쿼리 | **308 ms**, `Rows Removed by Filter: 199999`(사실상 전수) |
| EXPLAIN — COUNT(흔한 검색어) | **145 ms**, `Parallel Seq Scan` — 카테고리만 필터할 때(15ms)의 ~10배 |
| k6 target(50VU) | TPS 4.38/s, p50 7.18s, **p95 32.99s**, p99 46.95s, err 0% |
| k6 smoke(10VU) | p50 1.25s, **p95 7.99s** |

## 4. 수정 방법

- Alembic `migrations/versions/0002_p1_03_search_index.py`:
  `CREATE EXTENSION IF NOT EXISTS pg_trgm` + `ix_products_category_id`(btree) +
  `ix_products_name_trgm`/`ix_products_description_trgm`(GIN, `gin_trgm_ops`).
  **CONCURRENTLY 없이** 생성 — 무중단 인덱스 생성은 P2-15의 소재라 이번엔 그대로
  둠(CLAUDE.md §0-1, "심는 문제를 미리 고치지 않는다").
- `app/models.py`: `Product.__table_args__`에 위 3개 인덱스를 SQLAlchemy로
  선언해 마이그레이션과 모델 정의를 동기화. `INTENDED-ISSUE: P1-03` 주석 제거.
- `app/products/repository.py`: 해당 주석 제거, 인접한 P1-04(OFFSET)·P1-05
  (매 요청 COUNT) 표식은 범위 밖이라 그대로 둠.

## 5. 결과 (After)

### EXPLAIN — 단일 쿼리 (무경합)

| 쿼리 | Before | After | 배수 |
|---|---|---|---|
| 희소어 검색 | 308 ms (전수 필터) | 3.78 ms (GIN Bitmap) | ≈82× |
| COUNT(흔한 검색어) | 145 ms (Parallel Seq Scan) | 36 ms (Bitmap Heap) | ≈4× |
| COUNT(희소어) | ~308-364 ms | 1.4 ms | ≈100×+ |

**모든 경로에서 Seq Scan이 사라지고 Index Scan / Bitmap Index Scan으로
전환됨** — 백로그의 "EXPLAIN에서 Index Scan" 기준 충족.

### 부하 중 격리된 쿼리 지표 — P1-03 자체의 검증

`pg_stat_statements`로 "category+q" 검색 쿼리(=P1-03이 직접 담당하는 쿼리)만
분리하면:

| 지표 | Before | After |
|---|---|---|
| SELECT(검색) 평균 실행시간, 부하 중 | 4,640 ms | **7.8 ms (≈594×)** |

### 엔드포인트 전체(k6) — P1-03 fix 자체는 성공했지만 p95 게이트는 미달

| 지표 | Before | After |
|---|---|---|
| target(50VU) TPS | 4.38/s | 12.73/s (≈2.9×) |
| target(50VU) p50 | 7.18 s | 0.69 s (≈10.4×) |
| target(50VU) **p95** | 32.99 s | **17.91 s** (≈1.8×, 목표 `<200ms` 미달) |
| smoke(10VU) p50 | 1.25 s | 98.67 ms (≈12.7×) |
| smoke(10VU) p95 | 7.99 s | 4.13 s (≈1.9×) |

**원인**: `GET /products` 엔드포인트는 같은 요청 안에서 P1-03(검색)뿐 아니라
P1-05(매 요청 `COUNT(*)`, 아직 미수정)도 실행한다. `pg_stat_statements`를 보면
부하 중 COUNT 쿼리(mean 958~3,515ms)가 검색 쿼리(mean 7.8~971ms)보다 절대적으로
더 큰 비중을 차지 — P1-03 자체의 잔여 결함이 아니라, 옆에 남아있는 P1-05가
이제 지배적 병목으로 드러난 것이다. 동시성이 낮을수록(10VU) 이 간섭이 적어
개선 폭이 더 뚜렷하다(p50 12.7×).

### 회귀 확인

`make load S=mixed N=3 PROFILE=smoke`: checks 100%(882/882), err 0%,
p95 2.48s. 목록/상세/검색/주문/내역/로그인 전 경로 정상.

## 6. 요약

`name`/`description`에 `pg_trgm` GIN 인덱스, `category_id`에 btree 인덱스를
추가해 선행 와일드카드 `ILIKE`도 인덱스를 타게 만들었다. EXPLAIN·격리된 쿼리
지표로는 확실한 해결(검색 쿼리 594× 개선, Seq Scan 완전 소멸)을 확인했지만,
같은 엔드포인트에 공존하는 P1-05(매 요청 COUNT)가 아직 미수정이라 엔드포인트
전체 p95는 백로그 관문(200ms)에 못 미친다. 이는 결과를 그대로 기록한 것이며
(CLAUDE.md §0-7), P1-05가 완료되면 이 엔드포인트를 재검증해야 진짜 관문 통과를
확인할 수 있다 — 상세는 `docs/experiments/P1-03.md`의 "트레이드오프" 참고.
